# Open Questions

These decisions are not blockers for writing the first planning docs, but they should be answered before implementation hardens.

## Product Decisions

| Question | Default assumption |
|---|---|
| Is RedBolt a full C# reimplementation of rbfx rather than generated bindings over rbfx? | Yes. Native rbfx is reference/source for dependencies, not the runtime engine. |
| Should the first cube be allowed to use procedural geometry? | Yes, as long as it flows through resource and scene systems. |
| Should public APIs mirror rbfx? | Yes. Use near-1:1 API shape where possible and sensible. Prefer rbfx-compatible type/member/component/resource concepts unless there is a clear .NET reason to diverge. |
| Should public namespaces be `RedBolt.*`, `Urho3D.*`, or compatibility aliases? | Use `RedBolt.*` first, but keep type/member names and API shape close to rbfx. Add compatibility aliases/adapters only when useful for sample/resource portability. |
| Should math types be custom RedBolt structs or `System.Numerics` types? | Copy and adapt math types from /home/rk/Desktop/src/rbfx/rbfx/Source/Urho3D/CSharp/Managed/Math |
| Should logging be ported 1:1 from rbfx? | No. Use a C#-native logging solution and bridge native logs into it where needed. |
| Should rbfx serialization be ported 1:1? | No. Replace it with a C#-native serialization solution while preserving resource/scene compatibility goals where practical. |
| Should low GC pressure be a later optimization? | No. Minimize GC pressure from day one, especially in frame update, input, scene traversal, resource lookup, and rendering paths. |
| Should generated dependency bindings be public? | No, keep them internal until a dependency API is intentionally part of RedBolt's public surface. |
| Should RedBolt contain hand-authored dependency bindings? | No. All dependency bindings must be generated by SharpCpp from clang-parsed dependency headers. |

## Build Decisions

| Question | Default assumption |
|---|---|
| Should rbfx source be symlinked into `extern/rbfx-source`? | No. Use it as information source only. |
| Should RedBolt copy SharpCpp CMake helpers or wait for SharpCpp to expose consumer helpers? | Start with small RedBolt-local CMake helper; later upstream reusable helper into SharpCpp. |
| Which graphics backend should first cube target on this machine? | Auto-select Diligent Vulkan or OpenGL on Linux, whichever configures fastest. |
| Should native dependencies be static or shared? | Prefer static where dependency licenses/builds allow; keep `RedBolt.Native` as the generated-thunk shared library for P/Invoke. |

## Binding Decisions

| Question | Default assumption |
|---|---|
| How should RedBolt expose Diligent functionality? | Generate from Diligent headers with SharpCpp; hand-authored C# graphics APIs may sit above generated bindings. |
| How should RedBolt expose SDL functionality? | Generate from SDL headers with SharpCpp; hand-authored C# input/window APIs may sit above generated bindings. |
| Reuse SharpCpp.Support directly or fork RedBolt.Support? | Reuse directly for first cube. Re-evaluate only if public API identity becomes a problem. |
| Generate C++ thunks or expose C ABI manually? | Generate C++ thunks through SharpCpp. Do not add manual C ABI binding functions. |

## Resource Decisions

| Question | Default assumption |
|---|---|
| When should rbfx `.mdl` be supported? | Immediately after procedural first cube. |
| When should rbfx XML material/technique files be supported? | After shader and pipeline abstractions are stable. |
| Should resource paths mirror rbfx `CoreData;Data`? | Yes, but first cube may use generated/procedural resources. |
